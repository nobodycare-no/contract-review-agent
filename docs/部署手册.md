# 云端部署手册 — 合同审批审查 Agent（小白复现版）

> **写给谁**：只需要一台云服务器 + 一个已启动的 AutoDL GPU 实例，跟着命令**一行一行复制粘贴**就能完成部署。
> **全程约 40 分钟**（其中镜像构建 10~15 分钟，只需等）。
>
> **机器标记规则**：每个命令块开头标注在【哪台机器】上执行——【本机】=你自己的电脑、【服务器】=云服务器、【AutoDL】=GPU 实例终端。不要在错误的机器上敲。
>
> **两条铁律**：① 每一步末尾都有「✅ 自检」，看到预期输出才许往下走；② 卡住了直接翻到文末《常见故障速查表》，你遇到的 99% 都在里面。

## 0. 你需要准备的东西

| # | 东西 | 说明 |
|---|------|------|
| 1 | 云服务器一台 | Ubuntu 22.04，2核4G 起（手册以腾讯云为例） |
| 2 | AutoDL GPU 实例 | 已租用，且**已按本手册第 10 节启动 vLLM 并自检通过** |
| 3 | AutoDL 的公网地址 | 形如 `https://uXXXXX-xxxx.seetacloud.com:8443/v1`（实例页复制） |

## 1. 【本机】云服务器控制台：放行端口

在腾讯云控制台 → 你的服务器 → **安全组**，添加两条入站规则：

| 端口 | 来源 |
|------|------|
| 22/tcp | 你的 IP（或 0.0.0.0/0） |
| 18000/tcp | 0.0.0.0/0 |

✅ 自检：本机 `ssh root@<服务器IP>` 能登录。

---

## 2. 【服务器】系统初始化

```bash
sudo apt update
sudo apt -y upgrade
sudo apt -y install git curl ufw nano
sudo ufw allow 22/tcp
sudo ufw allow 18000/tcp
sudo ufw enable
```

✅ 自检：`sudo ufw status` 显示 22 和 18000 都是 ALLOW。

---

## 3. 【服务器】安装 Docker（腾讯云内网源，国内直连可用）

> 直接 `get.docker.com` 会被墙（报 SSL connection reset），必须用下面的内网源方式。

```bash
sudo apt -y install ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.cloud.tencent.com/docker-ce/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://mirrors.cloud.tencent.com/docker-ce/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
exit
```

> 最后一行 `exit` 是**故意退出重新登录**，让 docker 用户组生效。

✅ 自检（重新 ssh 登录后）：

```bash
docker --version          # 显示 Docker version 27.x 或更高
docker compose version    # 显示 Docker Compose version v2.x
```

## 4. 【服务器】配置 Docker 镜像加速（必做！否则第 8 步拉镜像卡死）

✅ 自检：输出里能看到 `https://mirror.ccs.tencentyun.com`。

## 7. 【服务器】配置环境变量

```bash
cp deploy/.env.example .env

```

保存退出：**Ctrl+O → 回车 → Ctrl+X**。

> `LLM_API_KEY` 默认 `sk-atguigu` 与 GPU 侧 `--api-key` 一致，一般不用动。

✅ 自检：`grep ADMIN_TOKEN .env` 显示的是你的新密码，不是 change-me-admin。

## 8. 【服务器】生产启动（首次约 10~15 分钟，只是等）

```bash

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

> 过程中会自动下载 mysql/python/node 镜像（走第 4 步的加速）并在容器里装依赖（pip 清华源、npm 国内源）。
> 若中途网络抖动报错，**原样重跑同一条命令**即可续上。

✅ 自检：

```bash

```

`app` 和 `mysql` 两行 STATUS 都是 `Up`（mysql 带 `(healthy)`）。mysql 首次初始化约 30 秒。

## 10. 【AutoDL】启动 vLLM（GPU 侧，唯一需要 GPU 实例终端的一步）

```bash
source /usr-data/venvs/model_services/bin/activate
pkill -f vllm.entrypoints; sleep 5

CUDA_VISIBLE_DEVICES=0 \
nohup python -m vllm.entrypoints.openai.api_server \
  --host 127.0.0.1 \
  --port 6006 \
  --model /usr-data/models/Qwen/Qwen3-8B \
  --served-model-name qwen3-8b \
  --api-key sk-atguigu \
  --dtype auto \
  --gpu-memory-utilization 0.85 \
  --max-model-len 12288 \
  --trust-remote-code \
  --enable-auto-tool-choice \
  --tool-call-parser hermes \
  >/usr-data/log/qwen.log 2>&1 &
```

> ⚠ `--enable-auto-tool-choice` 和 `--tool-call-parser hermes` **绝对不能漏**——没有它们，云端所有审查任务会 blocked（这是系统的零降级设计，不是故障）。
> 显存不足（16G 卡）把 `--max-model-len` 改回 `8192`。

等约 1~2 分钟模型加载完，然后 30 秒自检：

```bash
curl -s http://127.0.0.1:6006/v1/chat/completions \
  -H "Authorization: Bearer sk-atguigu" \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3-8b","messages":[{"role":"user","content":"用weather工具查北京天气"}],
       "tools":[{"type":"function","function":{"name":"weather",
                "parameters":{"type":"object","properties":{"city":{"type":"string"}}}}}]}' \
  | head -c 500
```

✅ 自检：输出 JSON 里有 `"tool_calls"` 和 `"finish_reason":"tool_calls"`。
若报 400 提示缺参数 → `tail -30 /usr-data/log/qwen.log` 检查启动命令是否真带上了那两个 flag。

## 12. 【本机浏览器】一次跑所有合同

1. 打开 `http://<服务器IP>:18000`
2. 先重置演示数据（5 张标准合同）——【服务器】上执行：
   ```bash
   curl -s -X POST http://127.0.0.1:18000/admin/reset-demo -H "X-Admin-Token: 你的ADMIN_TOKEN"
   ```
   ⚠ 此操作清空现有业务数据，恢复为 5 张标准演示合同。
3. 浏览器刷新首页 → **全选** 5 张单 → 点「开始批量自动审查」
4. **5 张立刻全部变「排队中」**，随后按并发度逐张变「AI 审查中」并行开跑
   （默认 3 张同时跑，`BATCH_CONCURRENCY` 可调），完成即变「已完成」；
   **随便刷新页面**——跟踪不会丢
5. 全部变「已完成」后，点任意一单进详情页，检查：
   - 合同基本信息（含「AI 核对」标记）
   - 按规则识别的风险 + AI 补充提示
   - 审查意见全文（首行「总风险等级：…」）
   - **审查留痕时间线**（每一次工具调用都带时间戳）
   - 「查看原件」能打开合同原文

✅ 自检：5 张全部「已完成」+「已写入评论区」，详情页时间线有完整工具调用记录。

## 常见故障速查表

| 症状 | 原因 | 处理 |
|------|------|------|
| `curl get.docker.com` 报 SSL reset | 境外源被墙 | 用第 3 节腾讯内网源方式 |
| `docker compose up` 拉镜像超时/卡住 | 未配镜像加速 | 回第 4 节配 daemon.json 并 restart |
| `service mock-approval has neither an image nor build context` | 用了旧版 prod 文件 | 确认 docker-compose.prod.yml 里**没有** mock-approval 字样（V2 是双容器） |
| `/health` 里 `llm.ok=false` | GPU 未启动/参数缺失/地址不对 | 走第 10 节自检；确认 .env 的 LLM_BASE_URL 与 vLLM 启动参数的端口/key 一致 |
| 审查任务变「需人工处理」，原因含 `LLM_RUN_FAILED` | 运行中 GPU/网络出问题 | GPU 恢复后详情页点「重新处理此单」（30~60 秒自动重跑） |
| 原因含 `tool choice requires --enable-auto-tool-choice` | vLLM 启动漏了两个 flag | 按第 10 节完整命令重启 vLLM |
| 前台批量「处理 X 张，跳过 Y 张忙单」 | 跳过的单当时正在别的请求里跑 | 稍后单独对它再点一次「审查/重试」即可 |
| 详情页显示「需人工处理」 | 见红框卡内的原因与「怎么办」指引 | 按指引操作；多数点「重新处理此单」即恢复 |
| 审查结论每次略有差异 | 大模型本质（温度 0.2 非确定性） | 特性非缺陷；同一合同结论通常收敛在同级 |

## 版本切换：GPU 版 ↔ GLM 版

> 两分支共用同一套 compose 管道（容器/网络/18000 端口/**数据卷**），
> 但代码是构建时拷进镜像的——**只 `git checkout` 切分支，运行中的容器毫不知情，继续跑旧逻辑**。
> 切换 = 取分支 → 核对 .env → 带构建重启，三步缺一不可。
> （当前 main 已是 GPU 版全量；GLM 云端 API 版在 `feat/cloud-glm53flash` 分支。）

### 先自检当前跑的是哪个分支（30 秒）

```bash
docker exec contract-review-agent-app-1 grep -c queued /srv/app/api/portal.py
```
输出 `0` = GPU 版在跑；输出 `5` = GLM 云端版在跑。
（另一信号：前台批量文案是「GPU 逐张处理」= GPU；「并行审查…排队中」= GLM。
浏览器看不准时先 **Ctrl+F5 强刷**——前端文件名随版本变化，旧缓存会骗人。）

### 切换 SOP（照抄）

```bash
# 0) 等当前批次跑完（账本 done+skipped=total）。
#    批次进行中强行重建：在途任务会被如实标记——审查中→需人工处理、排队中→回待处理，
#    数据不丢，切回来后详情页「重新处理此单」一键重跑。

# 1) 把目标分支取到服务器仓库（本仓库由 bundle 克隆，缺哪个分支先 fetch）
cd /opt/contract-review-agent
#    服务器能连 GitHub 时：
git fetch origin feat/cloud-glm53flash
#    离线时：【本机】重打含目标分支的 bundle 并 scp，然后服务器上：
#      git fetch /opt/cra.bundle feat/cloud-glm53flash:feat/cloud-glm53flash
git checkout feat/cloud-glm53flash            # 切 GLM 版
# git checkout main                           # 切回 GPU 版（main=GPU 全量）

# 2) 核对 .env（gitignored——切分支它原样不动，必须人工核对！最容易错的一步）
nano .env
#    GLM 版四行：LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
#                LLM_API_KEY=<智谱Key>          LLM_MODEL=glm-5.3-flash  LLM_THINKING=low
#    GPU 版三行：LLM_BASE_URL=<AutoDL地址>/v1   LLM_API_KEY=sk-atguigu   LLM_MODEL=qwen3-8b

# 3) 带构建重启（--build 少了等于没切！切 GPU 版前先按第 10 节启动 vLLM）
cd deploy && docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build

# 4) 复查
docker exec contract-review-agent-app-1 grep -c queued /srv/app/api/portal.py   # 5=GLM / 0=GPU
curl -s http://127.0.0.1:18000/health                    # 三组件 ok=true
curl -s -X GET http://127.0.0.1:18000/app/diag_llm       # "status":200 即 LLM 链路通
```

### 切换时数据会怎样

- MySQL 数据卷与附件卷**跨分支共享**：切换不丢任何审查记录与合同原件。
- 浏览器若显示旧界面，是缓存问题——强刷即可。
- GLM 版不需要 GPU；切回 GPU 版记得先开机 AutoDL 并启动 vLLM。
